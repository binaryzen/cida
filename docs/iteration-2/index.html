Customer Issue Dimension Analysis

Applying latent dimension discovery to a public JIRA ticket corpus  ·  Sourcetree for Windows  ·  2013–2023
What this is: A text-mining analysis of 1,000 public bug-tracker tickets submitted by Sourcetree for Windows users between 2013 and 2023. The goal is to surface the natural groupings in customer-reported issues — patterns that emerge from the language rather than categories defined by an engineer. A dimension in this context is one of those emergent groupings: a cluster of tickets that share vocabulary and behaviour even if they span multiple official product components or priorities.

Key findings:
  • 49% of tickets were never reviewed — a structural backlog problem, not a submission-quality problem
  • A single UI regression in v3.3.6 accounts for 1,193 community votes — more than any other defect category combined
  • Resolution outcome is determined by team triage decisions, not ticket content: creation-time features have essentially zero predictive power for whether a ticket gets fixed
  • The user base shows frustrated loyalty — users reinstall rather than leave, but engagement is driven by pain, not satisfaction

Text analysis approach

Crash logs and exception reports — the technical readouts .NET applications generate automatically when they crash — were stripped from ticket descriptions before analysis, so the algorithm doesn't overfit machine-generated error output. The remaining text was converted into a word-frequency table (300 terms weighted by how distinctive each term is across tickets; includes single words and two-word phrases). Two complementary methods were applied to find natural groupings:

  • NMF — Non-negative Matrix Factorization (10 topics, chosen by reconstruction error sweep across N=8–14): finds groups of tickets that share vocabulary. Each ticket gets a positive score for each topic; only tickets scoring above 0.07 on their dominant topic are assigned to it — 65 of 826 on-product tickets fall below this threshold and are treated as unclassified rather than forced into the nearest group. This is the primary method used throughout the report.
  • PCA — Principal Component Analysis (50 components, applied as cross-check): finds the directions of greatest variation across the full feature set including metadata; confirmed the same major themes as NMF but requires more interpretation effort.

Three preprocessing steps were required before the standard NMF pipeline produced clean topics: (1) Spam filter — 174 tickets mentioning no Sourcetree-domain term (git, commit, branch, clone, etc.) were removed before topic modelling; these were tickets filed against other products that leaked into the dataset and, having only generic bug-template language, clustered on template structure rather than product content. (2) Sourcetree git-command echo stripping — Sourcetree prints its own internal git invocations when an operation fails (e.g., git -c diff.mnemonicprefix=false -c core.quotepath=false fetch origin); without removal these machine-generated tokens formed a spurious "Git config options" topic. (3) Domain stop words — near-universal terms like "sourcetree", "windows", "problem", "issue" were added to the TF-IDF stop list; they appeared in too many tickets to discriminate between issue types and were anchoring a topic on their own.

Why NMF for topic discovery: NMF produces additive topic clusters — each ticket's score for a topic is a positive number that can be read directly as 'how much is this ticket about Topic X?' PCA produces axes that can go negative, making individual scores harder to interpret without domain knowledge. Both methods found the same major themes; NMF results are presented throughout because the topic weights are intuitive.

3   Triage Funnel — Operational Health

Triage is the first step after a ticket arrives: a team member reviews it and decides what to do — fix it, defer it to a backlog, mark it a duplicate of an existing report, or close it as outside scope. The chart below shows the final state of each of the 1,000 unique tickets in the dataset.

Key finding: 49.0% of all tickets are untriaged — sitting at "Needs Triage" with no action taken. The resolution rate is 13.3%. For every ticket that gets fixed, roughly four are never looked at. The triage funnel indicates a team significantly under-resourced relative to incoming volume.

The Gathering Interest state (13.8%) is a community voting mechanism the team uses to defer prioritisation. The top requests with no path to resolution include: Adding WinMerge to merge tool selection (28 votes); Add shortcuts for custom actions in Windows (17 votes); --allow-unrelated-histories (11 votes); Black Dark Theme (rather than Blue) (10 votes). Users who vote expect acknowledgement; the data shows no evidence these graduate.

4   Defect Landscape

Defect families are matched against ticket summaries (user-authored text). Pattern counts exclude description bodies to avoid inflation from .NET stack traces.

The v3.3.6 refresh regression — a single event dominates the corpus

The Refresh / auto-update family accumulated 1,193 community votes from a single regression shipped in v3.3.6 — the version is named in 77 ticket titles and bodies. The top ticket alone has 513 votes and 85 comments. The family has a 46% duplicate rate: 26 of 56 tickets are re-filings of the same bug. The core invariant that broke: after any operation that changes repository state, the UI must reflect that state without user intervention.

This is an integration test gap. A single automated test — run any state-changing operation (stage a file, commit, fetch, switch branch), then assert that the UI reflects the new state within 2 seconds — would have caught this before release.

Auth / credentials — chronic, structurally ignored

77 auth/credential tickets, 65 open (84%), and a near-zero duplicate rate (1%). The low duplicate rate is the key signal: these are not the same bug expressed differently — each new version introduces a new permutation of the same class of failure. The code responsible for saving and restoring account credentials has effectively no automated test coverage. The recurring pattern across tickets: configure an account → restart the app → account is gone.

Component health

  • Stash: 55.6% spam — inadequately gated submission channel
  • Beta: 47.1% spam — public beta channel attracted supplement spammers
  • Bitbucket: 9.2% resolution, 65.8% untriaged — Bitbucket integration work is systematically deprioritised
  • remote: 19.2% resolution rate — highest of any component

5   Topic Dimensions (NMF)

NMF was run on the 826 on-product tickets (after removing 174 off-product tickets). 65 tickets scored below the 0.07 minimum threshold and are excluded from topic-level charts; 761 tickets are classified into one of 10 topics.

Topic alignment (Cramér's V 0.10–0.27 across Issue Type, Priority, Component, and Outcome). Cramér's V is a 0–1 association score between two categorical groupings: 0 = no relationship, 1 = perfect correspondence. This range confirms the topics capture sub-structure within existing categories rather than merely restating them; Component shows the strongest alignment — topics are a finer-grained, text-derived version of the component taxonomy. Predictive modelling (Ridge regression, 5-fold cross-validation) showed that all creation-time ticket features combined — category, priority, component, and NMF scores — explain essentially none of the variance in resolution outcome (R² < 0.05). Whether a ticket gets fixed is determined by team triage decisions after filing, not by what the ticket says.

r = Pearson correlation with the resolution outcome scale (range: −1 to +1). Negative r = these tickets tend to resolve faster than average; positive r = these tickets tend to stay open longer. Significance: p<0.01 = highly significant; p<0.05 = significant; ns = not significant (result could plausibly be random noise).

The T2 Branch user is the core constituency

The T2 Branch tier (branching, merging, pull requests) has 7.4× the average vote rate of T1 Basic users, despite being a mid-sized tier by ticket count. These are collaborative developers doing real team workflows who care enough to engage the community — and who were hardest hit by the v3.3.6 refresh regression, because their daily workflow (branch → change → commit → confirm in UI) depends entirely on UI state staying current.

7   Sentiment & Loyalty

The dominant tone is frustrated loyalty. 8 tickets describe uninstalling and reinstalling as a troubleshooting step — a loyalty signal, not departure intent: a user who has given up simply leaves; someone who reinstalls is still trying to make the app work. Explicit intent-to-leave language ("switching to", "moving to") appears in 6 tickets. Positive sentiment ("love / great / best" about the product) appears in 1 ticket. Users are not leaving, but they are not delighted.

Lock-in mechanisms (descending signal strength)

  • Bitbucket double lock-in (152 tickets) — customers who host code on Atlassian's Bitbucket and use Sourcetree (also Atlassian) are tied to the ecosystem twice; switching the Git client means re-authenticating every repository connection
  • SSH / Pageant integration (17 tickets) — Pageant is the SSH key manager bundled with PuTTY (the standard Windows terminal); users route Sourcetree authentication through Pageant rather than the Windows keystore, creating a workflow dependency
  • Custom actions / scripts (15 tickets, 46 votes) — external tool calls wired into the UI
  • External diff / merge tools (8 tickets) — Beyond Compare, WinMerge, KDiff configured as default resolvers
  • Git flow UI (9 tickets) — release cadence built on the feature/ release/hotfix buttons
Notable absence: zero tickets mention GPG signed commits. GPG (GNU Privacy Guard) signing attaches a cryptographic identity to each commit, permanently tying a developer's history to a specific key pair — the deepest possible switching barrier. No tickets reference it, meaning this user base has not invested in identity-bound commits. Lock-in here is workflow habit and tool configuration, not identity.
